# Omuse photo colour regression corpus

These are pinned **Omuse `camera_raw` appearance references**, generated by the
existing Rust pipeline and explicitly reviewed before inclusion. They detect
unintended changes to its current output. They are **not Adobe Camera Raw parity
fixtures**, measured camera or chart colour targets, or proof of colour accuracy.

## Contents and provenance

`corpus.rs` defines an original, deterministic 256 × 16 RGBA8 fixture. Its rows
cover a full neutral ramp, near-black and near-white ramps, primary ramps, hue and
pastel wheels, eight warm skin-tone **proxies**, neutral patches, sixteen original
colour patches, warm/cool neutrals, two full alpha ramps and alpha boundary
values. The skin and chart colours are synthetic values chosen for regression
coverage, not measurements of people or a commercial colour chart.

`cases.json` contains fifteen named settings: identity; positive and negative
exposure; highlight/shadow recovery; contrasting tone controls; temperature/tint;
vibrance/saturation; master, per-channel and parametric curves; eight-sector HSL
mixer; point colour; global and split grading; and a combined sequence that can
reveal stage-order changes. These PNG reference recipes explicitly select
`toneMapping: "SmoothV1"`. Every nondefault case must change visible opaque
colour, not merely canonicalize transparent pixels. Exposure is also checked
independently for its expected direction, monotonicity and neutral preservation. The
corpus compares 61,440 output pixels across these cases.

Separate compatibility assertions preserve the serialized missing-version
`Legacy` behavior, including three recorded pixels that exhibit its known
near-black chroma amplification. Those legacy pixels are a **compatibility
contract, not approved appearance targets for new edits**. New-version tests
require exact RGBA identity for an untouched edit, bounded changes between
near-black input levels during tonal lifts, and monotonic neutral ramps under
shadow/highlight adjustments. Unknown tone-mapping versions must be rejected.

`baseline/` contains the input PNG, one output PNG per case and a manifest with
SHA-256 digests for PNG files, decoded pixel bytes, case definitions, fixture
definition, generator and the compiled `camera_raw.rs` source, plus the producing
application version and target platform. The recorded Git
revision is **context only**: the baseline was generated from a working tree, so
the embedded source digest identifies the pipeline file actually compiled. The
manifest is a provenance record, not a requirement that future source text has
an identical hash. Case-setting and input-pixel changes do require explicit
reference review. No test writes or updates the references.

## Independent comparison math

`color_metrics.rs` is test-only code. It does not use Omuse's production colour
conversion or filter helpers. It implements inverse sRGB transfer, the rational
sRGB-to-XYZ matrix and CIELAB using the **native D65 white**. This differs from
CSS `lab()`, whose coordinates use an adapted D50 white. Both colours in each
comparison use the same D65 white; no chromatic adaptation is applied here.
The transfer, primaries and white are documented in the
[W3C CSS Color 4 conversion specification](https://www.w3.org/TR/2026/CRD-css-color-4-20261009/#color-conversion-code).
Black, white, mid-gray, values on both sides of the sRGB transfer knee, the full
neutral ramp and all three primaries have analytic checks. Fixed primary and
knee values were separately evaluated with 60-digit decimal arithmetic.

The CIEDE2000 formula uses unit parametric factors. Its implementation is checked
against all **34 supplementary reference pairs** supplied by Sharma, Wu and
Dalal, including neutral, hue-wrap and near-180-degree branch cases. Expected
values are published to four decimal places, so the allowed absolute error is
0.000051; symmetry and identity are checked too. The TSV contains factual
numerical reference values from the authors' supplement. The Rust implementation
was written for this suite; it does not copy their MATLAB or spreadsheet code.

- [Authors' paper and supplementary material](https://hajim.rochester.edu/ece/sites/gsharma/ciede2000/)
- [Numerical reference pairs](https://hajim.rochester.edu/ece/sites/gsharma/ciede2000/dataNprograms/ciede2000testdata.txt)
- G. Sharma, W. Wu and E. N. Dalal, “The CIEDE2000 Color-Difference Formula:
  Implementation Notes, Supplementary Test Data, and Mathematical Observations,”
  *Color Research & Application* 30(1), 21–30 (2005), DOI 10.1002/col.20070.

## Failure limits

The suite compares each row independently over black, mid-gray (127) and white
mattes, composited in linear-light sRGB as a diagnostic comparison surface. This
is not a claim about the application's display compositing or ICC rendering.

| Guard | Limit |
| --- | --- |
| Per-row mean CIEDE2000, across all three mattes | 0.03 |
| Per-row 99th percentile CIEDE2000 | 0.35 |
| Maximum CIEDE2000 | 0.8 |
| Maximum rounded premultiplied RGB byte difference | 1 |
| Alpha compared with both reference and original input | Exact |
| Default identity, including hidden zero-alpha RGB | Exact RGBA |
| Nondefault zero-alpha output | Canonical `[0, 0, 0, 0]` |

These deliberately tight **regression tolerances** allow limited numerical
rounding while catching local or systematic changes. They are not universal
perceptual acceptability or just-noticeable-difference thresholds. Per-row means
keep a skin, shadow or highlight change from disappearing in an image-wide
average. Premultiplied byte guards suit the pipeline's existing quantization
boundaries; straight RGB can vary strongly at very low alpha.

Failure messages identify the case, purpose, chart row, metric limits and worst
pixel coordinates/values. Sensitivity tests deliberately swap channels, add a
colour cast, lift shadows, clip highlights, alter one patch pixel and damage
alpha, and require each alteration to fail. Invisible zero-alpha colour is
excluded from the appearance metric, while separate exact checks enforce the
pipeline's identity and transparent-pixel behavior.

## Run and review

From the repository root:

```sh
CARGO_BUILD_JOBS=2 cargo test --manifest-path rust/Cargo.toml --release --locked --features ui-test --test photo_color_corpus
```

For an intentional appearance change, generate candidates into a **new,
nonexistent directory** outside the committed references:

```sh
CARGO_BUILD_JOBS=2 cargo run --manifest-path rust/Cargo.toml --release --locked --features ui-test --example photo_color_baseline -- /tmp/omuse-colour-review-UNIQUE
```

The generator refuses any existing destination, including an empty one. It has
no force or bless switch. Review the actual old and candidate images, changed
settings/source, per-case colour differences and transparency behavior. Explain
why the new appearance is intentional before manually promoting the candidate
PNGs and manifest together. Merely making a failing test pass is not grounds to
replace a reference. Keep metric validation and mutation tests passing, and
rerun the corpus after promotion. Normal tests never invoke the generator.

## Limits

This small corpus covers deterministic RGBA8 colour and tonal operations, not
RAW demosaicing, 16-bit precision, wide-gamut/ICC accuracy, monitor appearance,
spatial sharpening/noise/optical corrections, subjective photo quality, or every
settings combination. It complements the preserved-kernel `camera_reference`
tests, real-photo qualification and separate import/export/precision checks;
it does not replace them. The initial local validation is on Linux. Other
platforms must run the same unchanged references before cross-platform
qualification is claimed.
